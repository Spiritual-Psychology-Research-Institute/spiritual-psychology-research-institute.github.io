# 메일로 홈페이지 고치기 — 설정 안내

김윤희 박사가 메일 한 통 보내면 홈페이지가 수정되는 파이프라인입니다.

```
고모 ── 메일 ──▶ 전용 Gmail
                    │  mail-inbox.yml (15분마다)
                    ▼
               GitHub 이슈 (라벨: site-request)
                    │  site-request.yml
                    ▼
             Claude가 수정 → PR 생성
                    │
                    ▼
            사람이 확인하고 Merge ──▶ 자동 배포
                    │  notify-requester.yml
                    ▼
            고모에게 "반영됐습니다" 메일
```

**검사를 통과하면 자동 머지됩니다.** 사람 승인 단계는 없습니다. 대신 머지 전
CI 검사가 관문입니다 (`.github/scripts/validate-site.mjs`).

검사가 보는 것:

- 바뀐 파일이 `index.html` / `404.html` / `docs/` 안인가.
  프롬프트에 적은 파일 제한은 지시일 뿐이므로 여기서 실제로 강제합니다.
- `div` 태그 균형
- 섹션 id / nav 링크 / JS `sections` 배열 세 곳의 일치

하나라도 걸리면 머지하지 않고 PR 을 열어둔 채 코멘트를 답니다.
머지되면 요청자와 관리자 모두에게 바뀐 파일 목록과 되돌리는 방법을
메일로 보냅니다. 되돌리기는 해당 PR 에서 Revert 를 누르면 됩니다.

## 1. 전용 Gmail 계정 만들기

기존 개인 메일을 쓰지 마세요. 앱 비밀번호를 GitHub에 넣어야 하므로 이 용도
전용 계정이 안전합니다. 예: `sai.site.bot@gmail.com`

만든 뒤:

1. 계정에 **2단계 인증**을 켭니다.
   <https://myaccount.google.com/signinoptions/twosv>
   앱 비밀번호의 전제 조건입니다. 2단계 인증이 꺼져 있으면 앱 비밀번호 메뉴가
   아예 나타나지 않고 "설정을 사용할 수 없습니다"만 뜹니다.
   두 번째 단계로 전화번호나 인증앱 중 하나를 등록해야 합니다.
2. <https://myaccount.google.com/apppasswords> 에서 **앱 비밀번호**를 만듭니다.
   16자리 문자열이 나옵니다. 이게 `MAIL_PASSWORD` 입니다.
   창을 닫으면 다시 볼 수 없으니 바로 GitHub 시크릿에 넣으세요.

> IMAP은 따로 켤 필요가 없습니다. Google이 개인 Gmail 계정의 IMAP 토글을
> 없애고 상시 활성으로 바꿨습니다. 설정 화면의 *전달 및 POP/IMAP* 탭에도
> 켜기/끄기 라디오가 더 이상 없습니다.

## 2. GitHub 토큰 만들기

<https://github.com/settings/tokens> 에서 **Fine-grained personal access
token**을 만듭니다.

- Repository access: 이 저장소만
- Permissions: `Issues: Read and write`, `Contents: Read and write`

> 왜 필요한가: 기본 `GITHUB_TOKEN`으로 만든 이슈는 **다른 워크플로를 트리거하지
> 않습니다.** GitHub의 무한 루프 방지 정책입니다. PAT로 만들어야 그다음
> 단계인 Claude 워크플로가 실행됩니다.

## 3. 저장소 시크릿 등록

Settings → Secrets and variables → Actions → *New repository secret*

| 이름 | 값 |
|---|---|
| `MAIL_USER` | 전용 Gmail 주소 |
| `MAIL_PASSWORD` | 위에서 만든 16자리 앱 비밀번호 |
| `ALLOWED_SENDERS` | 고모 메일 주소. 쉼표로 여러 개 가능 |
| `AUTOMATION_TOKEN` | 2번에서 만든 PAT |
| `ANTHROPIC_API_KEY` | <https://console.anthropic.com> 에서 발급 |

## 4. 동작 확인

0. 시크릿이 하나라도 비어 있으면 워크플로는 실패하지 않고 조용히 건너뜁니다.
   로그에 `시크릿이 아직 설정되지 않아 건너뜁니다` 가 찍히면 아직 덜 넣은 겁니다.
1. Actions 탭 → **메일 수신함 확인** → *Run workflow* 로 수동 실행
2. 전용 주소로 아무 메일이나 보내보고 이슈가 생기는지 확인
3. 이슈에 `site-request` 라벨이 자동으로 붙고 PR이 열리는지 확인
4. PR을 머지하고 회신 메일이 오는지 확인

`site-request` 라벨은 이미 만들어 두었습니다.

## 5. 고모께 안내할 내용

아래를 그대로 보내시면 됩니다.

> 고모, 홈페이지 고치고 싶은 거 있으시면 이 주소로 메일 보내주세요.
>
> **kakwaksai@gmail.com**
>
> 형식 같은 거 없어요. 평소 말씀하시듯 쓰시면 됩니다.
> "연구 섹션에 논문 하나 더 넣어주세요" 처럼요.
> 사진도 그냥 첨부하시면 되고요.
>
> 다 되면 답장으로 알려드릴게요. 고칠 데 있으면 그 답장에
> 다시 답장만 주시면 됩니다.

정말 이게 전부입니다. 고모는 GitHub 을 볼 일이 없습니다.

동작하는 것:

- 평문 한국어 요청 (형식 자유)
- 사진 첨부 — 사이트용으로 줄여서(긴 변 1600px, 위치정보 제거) `site-inbox`
  브랜치에 올라가고, Claude 가 가져다 넣습니다. 아이폰 HEIC 도 됩니다.
- 그 밖의 파일 첨부 — `site-inbox` 브랜치에 올라가고 이슈에 경로가 적힙니다
- 회신 메일에 대한 답장 — 인용된 원문은 자동으로 걷어냅니다
- 요청이 모호하면 **되묻는 메일**이 갑니다. 지어내지 않습니다.
  사이트 주소와 함께 "어느 부분을 어떻게 바꾸고 싶으신지" 를 묻고,
  어떻게 써주면 되는지 예시도 넣습니다. 답장으로 알려주시면 이어집니다.

## 자리를 비운 사이에도 도는가

메일 확인은 GitHub 예약 실행(cron)이 15분 간격으로 돌립니다. PC 를 꺼두어도
GitHub 서버에서 실행되므로 상관없습니다.

### 실제로는 cron 을 쓰지 않습니다

이 저장소에서 **GitHub 예약 실행이 전혀 동작하지 않았습니다.** 구축 후 3시간
동안 0회였고, 포크도 아니고 비활성도 아니고 승인 대기도 없으며 워크플로는
active 였습니다. 그래서 예약에 의존하지 않는 구조로 바꿨습니다.

```
하트비트 (mail-keepalive)  ── 5시간 15분 돌고 스스로 다음 회차를 띄움
   └─ 15분마다 ─▶ 메일 확인 (mail-inbox)
                     ├─ 새 메일 있으면 ─▶ 이슈 ─▶ Claude ─▶ PR ─▶ 검사 ─▶ 머지
                     └─ 하트비트 생존 확인 ─▶ 죽어 있으면 되살림
```

둘이 서로를 살립니다. 하트비트가 메일 확인을 깨우고, 메일 확인이 하트비트가
살아 있는지 봅니다. 어느 한쪽이 죽어도 다른 쪽이 복구합니다.

cron 설정은 보루로 남겨두었습니다. GitHub 쪽이 정상화되면 자연히 한 겹 더
두터워지고, 계속 안 돌아도 상관없습니다.

**하트비트는 우회책입니다.** 러너 하나가 대부분 잠든 채 5시간을 점유합니다.
공개 저장소라 Actions 시간은 무료지만 깔끔한 구조는 아닙니다. 아래 Apps
Script 방식으로 옮기면 `mail-keepalive.yml` 을 지워도 됩니다.

### 예약 실행 일반

**GitHub 예약 실행은 보장된 시각이 아닙니다.** 부하가 몰리면 지연되거나
건너뜁니다. 그래서 두 가지를 더 해두었습니다.

- 실행 시각을 매시 `:07 :22 :37 :52` 로 두었습니다. 정각 부근이 가장 혼잡해서
  `*/15` 처럼 `:00` 을 때리는 설정은 밀리기 쉽습니다.
- 즉시 깨우는 경로를 열어두었습니다. 아래 한 줄이면 예약을 기다리지 않고
  바로 메일함을 확인합니다.

  ```sh
  gh api repos/:owner/:repo/dispatches -f event_type=check-mail
  ```

급한 수정이라 지금 당장 반영되어야 한다면 이 명령을 쓰거나, Actions 탭에서
**메일 수신함 확인 → Run workflow** 를 누르면 됩니다.

### 더 확실하게 하려면 — Gmail 이 직접 깨우기

GitHub 예약이 계속 밀리면, Gmail 쪽에서 밀어주는 방식으로 바꿀 수 있습니다.
폴링이 사라지고 메일 도착 후 1분 안에 처리됩니다.

1. <https://script.google.com> 에서 새 프로젝트를 만듭니다
   (반드시 `kakwaksai@gmail.com` 으로 로그인한 상태에서).
2. 아래 코드를 붙여넣습니다.

   ```javascript
   const REPO = 'Spiritual-Psychology-Research-Institute/spiritual-psychology-research-institute.github.io';

   function checkMail() {
     // 안 읽은 메일이 있을 때만 GitHub 을 깨운다.
     if (GmailApp.search('is:unread in:inbox', 0, 1).length === 0) return;

     UrlFetchApp.fetch(`https://api.github.com/repos/${REPO}/dispatches`, {
       method: 'post',
       contentType: 'application/json',
       headers: {
         Authorization: 'Bearer ' + PropertiesService.getScriptProperties().getProperty('GH_TOKEN'),
         Accept: 'application/vnd.github+json',
       },
       payload: JSON.stringify({ event_type: 'check-mail' }),
       muteHttpExceptions: true,
     });
   }
   ```

3. 프로젝트 설정 → **스크립트 속성**에 `GH_TOKEN` 을 추가하고 값으로
   `AUTOMATION_TOKEN` 과 같은 PAT 를 넣습니다.
4. 트리거 → **트리거 추가** → `checkMail` / 시간 기반 / 분 단위 타이머 /
   1분마다.

GitHub 예약 실행은 그대로 두어도 됩니다. 둘 다 돌아도 같은 메일을 두 번
처리하지 않습니다 — 처리한 메일은 읽음으로 표시되고, `concurrency` 설정이
동시 실행을 막습니다.

## 알아둘 것

### 이 저장소는 공개입니다

이슈 내용과 Actions 로그는 **누구나 볼 수 있습니다.** 그래서:

- 보낸 사람 주소는 이슈에 기록하지 않고, 로그에서도 `::add-mask::`로 가립니다.
- 하지만 **메일 본문은 이슈에 그대로 들어갑니다.** 어차피 홈페이지에 올릴
  내용이라 대부분 문제없지만, 개인적인 이야기를 같이 적으시면 공개됩니다.
- 더 엄격하게 하려면 자동화만 **비공개 저장소**로 분리하고 거기서 이 저장소에
  PR을 여는 구조로 바꾸면 됩니다. 필요해지면 그때 옮기는 게 낫습니다.

### 첨부파일

`site-inbox` 브랜치에 올라갑니다. 이 브랜치는 배포와 무관하고,
`main`에 머지하지 않는 한 사이트에 나타나지 않습니다. 가끔 비워주세요.

**사진**은 올리기 전에 `prepare-image.mjs` 가 손봅니다.

- 긴 변 1600px JPEG 로 줄입니다. 휴대폰 원본 11MB 가 500KB 안팎이 됩니다.
- 휴대폰 회전 정보대로 바로 세웁니다.
- **메타데이터를 지웁니다.** 촬영 위치(GPS)가 공개 저장소에 올라가지 않습니다.
- 아이폰 HEIC 는 JPEG 로 바꿉니다.
- 200px 보다 작은 그림은 메일 서명의 아이콘으로 보고 건너뜁니다.

줄인 사진은 사이트에서 쓸 경로 그대로(`assets/uploads/<시각>-<번호>.jpg`)
올라가므로, Claude 는 `git checkout origin/site-inbox -- <경로>` 한 번으로
가져와 `index.html` 에 넣습니다. 사진 원본은 어디에도 남지 않습니다.
사진 외 첨부는 예전처럼 `inbox/` 아래에 그대로 올라갑니다.

### 비용

**돈이 드는 것은 Claude API 뿐입니다.** GitHub Actions 는 공개 저장소라
무료이고, 15분 주기 폴링과 하트비트도 전부 무료 범위입니다. 메일이 오지
않으면 비용은 0 입니다.

구축 당일 Opus 로 돌았을 때의 실측치입니다.

| 요청 | 턴 | 비용 |
|---|---|---|
| 되묻기만 (PR 없음) | 5 | $0.16 |
| 문구 한 줄 수정 | 10 | $0.22 |
| 대비 개선 | 26 | $1.01 |
| "더 예쁘게 뭔가 많이" | 55 | $2.79 |

모델을 지정하지 않으면 Opus(1M 컨텍스트)로 돌아 이렇게 나옵니다.
**Sonnet 으로 내렸습니다.** 같은 난이도(문구 한 줄)를 Sonnet 으로 다시
돌린 실측은 8턴 **$0.10** 으로, Opus $0.22 의 절반쯤입니다. 모델 단가
차이만큼 그대로 줄지는 않습니다 — 파일을 읽고 도구를 쓰는 턴 비용이
모델값과 별개로 깔리기 때문입니다.

구조 검사(CI)가 실수를 잡아주므로 품질 위험은 낮습니다. 실제로 Sonnet 이
푸터 문구를 정확히 고치고 "이 표현이 자연스러운지 확인해달라" 고
덧붙였습니다.

**지금은 싼 모델이 먼저 하고, 안 되면 좋은 모델이 이어받습니다 (2026-09-23).**

| 요청 | 1차 | 2차 |
|---|---|---|
| 사진 없는 요청 | Haiku 4.5 ($1 / $5) | 1차가 검사를 통과한 PR 을 못 만들면 Sonnet 5 ($2 / $10) |
| 사진이 첨부된 요청 | Sonnet 5 | 없음 |

(단가는 입력/출력 100만 토큰당)

Haiku 의 결과는 **검사를 통과한 PR 일 때만** 그대로 씁니다. PR 없음, 검사
실패, 되묻기, "이미 반영됨", 중간에 멈춤은 모두 Sonnet 이 처음부터 다시
봅니다. Haiku 는 모양에 관한 요청(선, 색, 크기, 배치)이면 손대지 않고 바로
넘기게 했습니다. 요청자에게는 마지막 모델의 답만 갑니다.

지금까지 온 요청 11건에 비추면 이렇게 나뉩니다.

| 요청 | 예 | 처리 |
|---|---|---|
| 문구 바꾸기 | #14 #18 #20 #27 | Haiku |
| 긴 글 넣기 | #29 부버 '사이' 글 | Haiku (원문 그대로, 기존 글과 같은 구조로) |
| 이미 반영된 요청 | #22 #23 #24 | Haiku 가 보고 Sonnet 이 확인, "이미 있습니다" 메일 |
| 모양 바꾸기 | #25 제목 옆 줄 지우기 | Haiku 가 바로 넘김, Sonnet |
| 막연한 대규모 요청 | #9 "예쁘게 더 많이" | 새로 디자인하지 않고 예를 들어 되묻기 |
| 수정 요청이 아님 | #13 "장손아 이게 니꺼니?" | 짧은 답장 (되묻기 문구 없이) |

프롬프트는 `.github/prompts/` 에 있습니다. 요청자의 말투("바꿔조", "지워조"),
따옴표가 다른 인용("사이에서 찾다" vs 사이트의 ‘사이’에서 찾다), 섹션을 번호로
부르는 것("03.연구") 같은 실제 사례를 적어 두었습니다.

프롬프트에서 `index.html` 을 통째로 읽지 말고 Grep 으로 위치를 찾아 그
근처만 읽게 했습니다. 2000줄짜리 파일을 턴마다 다시 읽는 것이 모델 단가보다
큰 비용이었습니다. Haiku 는 25턴에서 끊습니다. 오래 헤매는 것 자체가 넘겨야
한다는 신호입니다.

바꿀 수 있는 저장소 변수:

- `CLAUDE_MODEL` — 1차 모델. `claude-sonnet-5` 를 넣으면 1차부터 Sonnet 이고 2차는 없습니다.
- `CLAUDE_STRONG_MODEL` — 2차와 사진 모델 (기본 `claude-sonnet-5`)
- `CLAUDE_FAST_MAX_TURNS` — 1차 턴 상한 (기본 25)
- `CLAUDE_MAX_TURNS` — 2차와 사진 턴 상한 (기본 40)

저장소 변수는 Settings → Secrets and variables → Actions → Variables 에서
만듭니다. 값 예: `claude-sonnet-5`, `claude-opus-5`.

**지출 상한을 걸어두세요.** <https://platform.claude.com/settings/billing>
의 월 지출 한도가 기본 $1,000 입니다. 이 용도라면 월 $10~20 으로 낮춰도
충분하고, 무언가 잘못 돌 때의 안전망이 됩니다.

### 요청을 못 알아들었을 때

무엇을 어떻게 바꿔야 할지 알 수 없는 메일이 오면 (안부 인사, 링크만 보낸
메일, "예쁘게 해줘" 처럼 막연한 요청) PR 을 만들지 않고 **되묻는 메일**을
보냅니다. 사이트 주소와 함께, 화면을 보고 어느 부분을 어떻게 바꾸고 싶은지
답장으로 알려달라고 안내합니다.

이게 없으면 요청자는 아무 답도 받지 못합니다. Claude 가 PR 본문에 질문을
적어봐야 GitHub 을 보지 않는 사람에게는 닿지 않습니다.

### 이미 반영된 요청일 때

요청한 내용이 이미 사이트에 있으면 되묻는 메일이 아니라 **"이미 홈페이지에
있습니다"** 메일이 따로 갑니다. 화면 어디에 있는지, 새로고침하는 법을
알려주고 이슈를 닫습니다.

예전에는 둘이 같은 틀이었습니다. "이미 반영되어 있습니다" 가 "이해하지
못했습니다 ... 어떻게 바꾸고 싶으신지 알려주세요" 사이에 끼어 나갔고,
요청자는 같은 요청을 세 번 다시 보냈습니다 (이슈 #22~24, 2026-09-22).
한 번은 Claude 가 댓글 표시(`<!--ASK-->`)를 빠뜨려 설명 없이 기본 되묻기
문구만 나가기도 했습니다. 이제 표시가 없는 댓글은 판단을 덧붙이지 않고
댓글 내용만 그대로 전합니다.

### 반영 메일에 무엇이 바뀌었는지 적습니다

반영 메일에 예전에는 요청 메일 제목만 되풀이했습니다("수정 내용: RE: 홈페이지
수정이 반영되었습니다"). 무엇이 바뀌었는지 알 수 없어 요청자가 이미 고쳐진
것을 다시 요청하는 원인이 됐습니다. 이제 Claude 가 PR 본문의
`<!--SUMMARY-->` 칸에 화면 기준으로 1~3줄 요약을 적고, 그 요약이 메일에
들어갑니다.

### 실패하면 알려줍니다

메일 확인이나 수정 작업이 실패하면 `kakwak123@gmail.com` 으로 알림 메일이
갑니다. 무인 운영에서 가장 위험한 건 침묵이 정상과 구분되지 않는 것이라,
파이프라인이 죽으면 반드시 티가 나게 해두었습니다. 흔한 원인은 앱 비밀번호
폐기, API 크레딧 소진, PAT 만료입니다.

### 요청이 빗나갈 때

이슈 본문은 신뢰할 수 없는 입력으로 취급합니다. 메일 본문에 "규칙을 무시하고
..." 같은 문장이 섞여 들어와도 워크플로의 지시가 이깁니다.

사람 승인이 없는 대신 기계가 강제하는 것:

- **수정 가능 파일** — `index.html`, `404.html`, `docs/`, 메일로 온 사진
  (`assets/uploads/` 의 jpg/png/webp, 1.5MB 이하) 뿐입니다.
  `.github/` 아래를 건드리면 머지되지 않습니다. 프롬프트의 지시가 아니라
  CI 가 diff 를 보고 판정합니다.
- **구조 불변조건** — `div` 균형, 섹션 id / nav 링크 / JS `sections` 배열의 일치.
- **사진** — `index.html` 이 가리키는 `assets/` 파일이 실제로 있는지(깨진 그림 방지),
  모든 `<img>` 에 `alt` 가 있는지.

검사기와 메일 스크립트는 작업 시작 때 `main` 의 것을 따로 복사해 두고 그것만
씁니다. 예전에는 PR 을 체크아웃한 뒤 PR 안의 검사기를 돌렸기 때문에, 검사기를
고친 PR 이 자기 검사를 통과할 수 있었고 검사 실패 알림도 PR 의 스크립트가
메일 비밀번호를 쥔 채 실행했습니다.
- **명도 대비 회귀** — 색 변경으로 기존보다 나빠지면 걸립니다.

기계가 볼 수 없는 것은 **문장의 내용과 판단**입니다. 여기에 대한 방어는
두 가지입니다. Claude 에게 "이 PR 은 사람 확인 없이 배포된다" 고 알려
확신 없는 변경을 하지 않게 했고(실제로 모호한 요청에는 내용을 지어내지 않고
PR 에 되묻습니다), 머지되면 바뀐 파일 목록과 함께 메일이 갑니다.

이상하면 해당 PR 에서 **Revert** 를 누르면 즉시 되돌아갑니다.
